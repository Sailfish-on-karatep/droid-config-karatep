# Cap video recording at 1080p.
#
# Without this, jolla-camera records at the largest size the camera HAL
# advertises -- 3840x2160 on the rear sensor -- and nothing on karatep can
# encode that. /vendor/etc/media_codecs.xml, which is what MediaCodec actually
# enforces, caps the hardware encoder at
#
#     <MediaCodec name="OMX.qcom.video.encoder.avc" type="video/avc">
#         <Limit name="size" min="96x96" max="1920x1088" />
#
# and the Codec2 software fallback is no better: c2.android.avc.encoder allows
# max="2048x2048" with block-count 1-8192, against the 240x135 = 32400 blocks
# 2160p needs, so it returns -EINVAL. 1080p is also Qualcomm's documented
# ceiling for the Snapdragon 430, and the HAL's own defaults agree with it
# (video-size=1920x1080, preferred-preview-size-for-video=1920x1080). The
# 3840x2160 in video-size-values is the ISP's capability, not the encoder's.
#
# droidcamsrc encodes internally, via DroidMediaRecorder, so the failure lands
# inside the camera stack rather than downstream of it: "DroidMediaRecorder:
# Cannot create codec", then "DroidMediaBufferQueue: Client wasn't able to
# handle a received frame" forever, and a black viewfinder. Full write-up:
# karatep-port/docs/rca/camera-dies-on-record.md
#
# Do not believe /vendor/etc/media_profiles_V1_0.xml here. Its VideoEncoderCap
# for h264 claims maxFrameWidth="3840" maxFrameHeight="2160", which is wrong --
# that element is advisory and read only by the legacy CamcorderProfile path.
# The CamcorderProfiles in the same file stop at quality="1080p".
#
#
# THIS IS THE WHOLE FILE, AND THAT IS DELIBERATE.
#
# Ports commonly copy a large jolla-camera-hw.txt from another device, with
# [apps/jolla-camera/primary/image] sections setting imageResolution,
# viewfinderResolution, flashValues, whiteBalanceValues, focusDistanceValues,
# isoValues and so on. On this jolla-camera none of that is read. Verified
# three ways rather than assumed:
#
#   * src/settings.qml in the installed package puts the per-mode
#     ConfigurationGroup at  position + "/" + captureMode  where position is
#     "back" or "front" -- so "primary"/"secondary" sections are dead names to
#     begin with, whatever keys they hold. (Jolla's own stock
#     jolla-camera.txt still ships primary/secondary. It is equally inert.)
#   * That group declares only iso, flash, exposureMode, meteringMode, timer
#     and aspectRatio. Grepping every installed .qml for the resolution and
#     *Values key names returns nothing.
#   * Live dconf confirms it: the running app reads and writes [back/image]
#     and [back/video], and leaves any [primary/*] keys untouched.
#
# Resolutions, flash modes, focus modes and white balance are all derived at
# runtime instead, by CameraConfigs (src/cameraconfigs.cpp) from what
# QtMultimedia reports, and picked per aspect ratio in CaptureView.qml. The
# only dconf input to that is the cap below, applied in cameraconfigs.cpp as
#
#     QVariant value(MDConfItem("/apps/jolla-camera/maxVideoResolution").value());
#     QStringList values = value.toString().split('x');
#
# which is why it is a 'WIDTHxHEIGHT' string and not a list.
#
# The matching /apps/jolla-camera/maxImageResolution exists upstream but is
# absent from the build installed here, so stills cannot be capped this way --
# not that they need to be. They already come out at the sensor's full size
# (rear 4632x3474, front 3264x2448, confirmed on captures taken before this
# file existed), which is what a 16 MP and an 8 MP sensor should give.
#
# Anything added below beyond this key needs to be checked against the
# installed jolla-camera first. It is very easy to add config here that looks
# right, changes nothing, and quietly misleads the next person.

[apps/jolla-camera]
maxVideoResolution='1920x1080'
